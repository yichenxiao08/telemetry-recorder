# Open questions and conservative choices

These items need product confirmation eventually. Implementation proceeds with the choices below so intake remains bounded and evidence is not lost.

1. **Run grouping and identities.** The draft says web `run_id` is a trace ID, while ML uses `signalscout.run.id`; it does not specify mixed or absent identity attributes. Choice: ML resource run ID takes precedence; otherwise each trace ID identifies a web run. Logs/metrics with a run ID attach to the ML run. Uncorrelated ambient signals are stored in dedicated ambient tables, never discarded or guessed into a run. No trace ID means no fabricated web run.
2. **Idle-timeout finalization and late data.** “Late-arriving data must attach to an existing run” conflicts with finalizing and marking rows closed after idle timeout. Choice: late records may attach to a closed run only when their explicit run ID/trace ID matches; closed status remains closed and outcome is recomputed from available evidence. Unknown identities create/open a run only when the payload itself contains enough identity and workload metadata. Finalization uses last-seen activity and an injectable clock for tests.
3. **Single SQLite writer.** The schema uses globally unique span IDs but does not state duplicate/retry semantics or shutdown behavior. Choice: one bounded intake queue and one writer goroutine own all writes; each batch is one transaction; duplicate stable IDs are idempotent upserts; queue full is immediate 503 with Retry-After; graceful shutdown drains queued writes before closing. Reads use a separate read-only pool. Ambient signals use separate tables so they remain stored without invented run IDs.
4. **OTLP JSON and protobuf.** JSON encoding, content type parameters, partial success, unknown fields, and request limits are unspecified. Choice: protobuf is default when content type is absent; accept `application/x-protobuf` and OTLP JSON `application/json` (including `+json`), decode via official OTLP proto types, allow unknown JSON fields, reject malformed/unsupported types with 4xx, cap decompressed bodies, and respond with OTLP-compatible empty success response. gzip is decoded before the cap is enforced.
5. **Context attachment.** No propagation mechanism is defined for logs/metrics to a run beyond resource attributes, and span events differ from standalone logs. Choice: use `signalscout.run.id` first; otherwise use trace ID for trace-correlated logs. Standalone log records are persisted as events with their original body, attributes, timestamp, trace/span IDs and are ambient if no run identity exists. Metrics similarly attach by run ID or remain ambient; do not infer based on time proximity.
6. **Log template normalization.** The transform is not specified and risks merging materially different messages or leaking high-cardinality values. Choice: preserve original body; store a second deterministic template generated by replacing quoted strings, UUIDs, IPs, and numeric tokens with `{}` while retaining word structure. Do not use templates as identities, and do not normalize attributes. This is deliberately conservative and lossy only in the derived field.
7. **Web workload/outcome and thresholds.** Root span selection, missing HTTP status, configurable duration thresholds, and threshold config format are underspecified. Choice: root is parentless span; workload prefers `http.route`, then span name; fail on OTEL error status or HTTP status >=500, otherwise degraded only if a configured workload threshold is exceeded; missing threshold/status means pass. ML non-finite values fail. Outcomes are recomputed on close and late attachment.
8. **Metric point variants.** The initial schema has one float value but OTLP supports integer, histogram, summary, and exponential histogram. Choice: persist numeric scalar points (gauge/sum scalar); preserve unsupported aggregate payloads as JSON evidence records rather than silently flattening buckets or dropping them. This milestone's point throughput covers scalar points.
9. **Throughput acceptance.** The plan requires 5,000 spans/sec on a laptop but specifies no hardware, payload, or measurement command. Choice: provide a repeatable Go benchmark and report its actual run only when executable on the project owner's laptop. Do not claim a number from unmeasured or unavailable hardware.
10. **Plan filename and module owner.** Workspace contained only `plan (1).md`, not the referenced `plan.md`, and no Git metadata. Choice: copy the supplied complete plan unchanged to `plan.md`; initialize Git locally. Use `github.com/signalscout/signalscout` as the provisional module path until an owner namespace is chosen.
11. **Native toolchain.** Go/Task/linter availability is not specified. Choice: keep Taskfile and CI Windows-native; avoid shell scripts; do not weaken checks if tools are unavailable. Document inability to execute rather than asserting acceptance.
