# Probe scan JSON contract, version 1

Original top-level keys (additions below): schema_version (integer 1), candidates and unresolved (arrays of Candidate), coverage, exclusions, errors, truncations and limits. Arrays are always present, including empty lists. Candidate keys: file (relative slash path), line (positive integer), function, signals (string array), selector, unsupported_reason. Later candidate construction must supply either selector or a nonempty unsupported_reason; foundation emits no candidates.

Coverage keys: eligible, parsed, read (nonnegative integers), bytes (nonnegative integer), complete (boolean). Eligible excludes pruned trees; enumeration failures mean the true eligible total is unknown. complete requires no errors or truncations and describes only eligible scope, never excluded trees. Parsed/read and exclusions must always be shown together. Entry arrays contain path and reason; no source or exception text. Limits: max_files (1..2000), max_bytes (1..20000000). Stable traversal order and no timestamps make identical trees/settings byte-stable. JSON files are created exclusively, never overwritten.

Parsing uses a fixed Python ast.parse program with source bytes on stdin, -E -s -B, five-second per-file deadline and 1 KiB output bound. No target imports or execution. The trusted interpreter standard library starts normally; this is not a sandbox against a compromised interpreter. Syntax coverage depends on Python version. A stable source tree is required: concurrent hostile replacement of parent directories is outside this foundation's filesystem threat model. Links and reparse points found during enumeration are rejected rather than followed. Total parsing time can reach five seconds per admitted file. Enumeration now enforces the additive resource budgets below; filesystem syscall duration remains unbounded.

## Additive steps 3-4 fields (schema_version remains 1)

Candidate retains every existing key and adds details (array of Signal), score, rank, tie_count (integers), config (YAML fragment string; empty for unsupported) and hot (boolean). Signal has kind, file, line, fact, tier. kind is one of the six implementation-note names. tier is observation except partial_dict_key, which is association; this is syntactic association, not statistical or causal evidence. signals remains the deduplicated kind array, and score is its length. Details provide file:line provenance. selector is empty when unsupported_reason is nonempty. Config capture is {}, i.e. OFF. Hot configs suggest incomplete deterministic sampling; text explains unknown unsampled calls and optional paired queue placeholders with memory estimates. Queue settings are never defaults. Each section is capped independently by --limit 1..200 (default 20). Rank and tie_count describe the full section before its cap. Truncations distinguish per-file analysis, scan read limits, primary and unresolved post-ranking limits. Complete is false for any error or truncation.

The original fixed parser remains for parse-only tests. CLI analysis uses a fixed embedded AST program with 4 MiB output cap and 256 candidate entries per file, reporting omitted counts; failures remain errors. Module resolution is relative to explicit --import-root, otherwise root-level modules and uninterrupted __init__.py package chains only. Ambiguous src/namespace layouts have no selector. No new top-level keys were introduced.

Hot candidates additionally expose advice (string), carrying the same INCOMPLETE sampling, unknown-unsampled and optional paired queue/memory warning as text, including unsupported hot call sites.

## Additive step 5 field

probe_command is an array of PowerShell instruction lines using the shared doctor renderer. CLI text prints the same array under a heading stating that --doctor is required. Existing fields and schema_version 1 remain unchanged. Parse-only library reports default to an empty array; CLI reports include the block with explicit unresolved-path placeholders. Rendering is static inspection only; the AST parser retains its existing subprocess behavior.

## Additive enumeration fields (schema_version remains 1)

enumeration contains limits (max_entries, max_path_bytes, max_depth, max_diagnostics), entries (admitted entries in fully read directories, including non-Python entries; the incomplete current directory is rolled back), and complete (no enumeration error, exhaustion, cancellation or omitted enumeration diagnostic). diagnostics_omitted counts diagnostic entries omitted across errors/exclusions/truncations after their shared cap. coverage.eligible_known distinguishes a known total from discovered paths. All original keys remain present; consumers must permit additive keys.

Defaults/caps and accounting appear in design-probe-scan.md. On enumeration resource exhaustion no source is admitted, eligible=0, eligible_known=false and coverage.complete=false. On directory/metadata errors, eligible counts discovered paths and the true total is unknown. Processing cancellation after completed enumeration retains the known eligible total but complete=false. Diagnostic overflow never reports a complete scan. A truncation diagnostic may itself be omitted, so check diagnostics_omitted as well as arrays. Text explicitly reports unknown totals and lack of global top-N guarantees. Stable identical trees/settings produce deterministic reports; partial over-budget directory entries are never processed.
